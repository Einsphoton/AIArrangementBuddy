# ACE-Step `extract` 能否做分轨？—— 实测结论：不能（它不是分离模型）

> 2026-11-13 · 引擎 `acestep.cpp 07abf07` · 用户问题：「是不是这个模型根本做不到分轨生成？」
> **答：是的，做不到。** 这不是参数调优问题，是任务定义问题。
> 复现脚本：`.verify-audio/extract_probe.py`、`extract_probe2.py`、`stem_similarity.py`、`reconstruct_test.py`

---

## 一、看代码就已经存疑

`music-gen/ace-step/acestep/constants.py:133`：

```python
"extract": "Extract the {TRACK_NAME} track from the audio:",
```

这与 `lego` 的 `"Generate the {TRACK_NAME} track based on the audio context:"` 共享同一条
**diffusion 采样路径**（`inference.py:36-38` 把 `extract` 与 `lego` 一起放进
`DIRECT_CONDITIONING_TASKS`），区别只在文本指令与 `track` 字段。

`extract` 没有独立的分离网络、没有频谱掩码、没有相位重建。
ACE-Step 是 **text-to-music 生成模型**，`extract` 是其 DiT 上的一种"条件生成"任务
——**按提示从源音频条件性地重新合成**，不是"从混音里减去其他乐器"。

## 二、决定性实验：给纯钢琴源，抽取根本不存在的乐器

我合成了一段**保证只含钢琴**的 20s 音频（C 大调琶音 + 谐波衰减包络），
然后让引擎分别 extract `drums` / `guitar` / `bass` / `keyboard`。

**如果 extract 是真分离**：抽"本不存在的鼓"应当接近静音（没有内容可分），
且四种乐器应得到**彼此完全不同**的结果。

**实测结果**：

| 抽取目标 | 输出 RMS | 相对源 | vs 源相关 | low | mid | high |
|---|---|---|---|---|---|---|
| 源（纯钢琴） | -11.26 dBFS | — | — | 1.8% | 50.1% | 1.1% |
| → drums | **-14.46 dBFS** | -3.20 dB | **+0.903** | 0.8% | 55.7% | 0.7% |
| → guitar | **-13.86 dBFS** | -2.60 dB | **+0.932** | 0.8% | 55.8% | 0.6% |
| → bass | **-14.23 dBFS** | -2.96 dB | **+0.933** | 0.7% | 55.4% | 0.6% |
| → keyboard | -13.27 dBFS | -2.01 dB | +0.950 | 0.7% | 55.3% | 0.5% |

**从只含钢琴的音频里"抽出"了鼓、吉他和贝斯，而且能量只比源低 3 dB。**

四路输出**两两相关**：

```
              drums    guitar      bass  keyboard
drums         1.000     0.990     0.994     0.986
guitar        0.990     1.000     0.998     0.996
bass          0.994     0.998     1.000     0.997
keyboard      0.986     0.996     0.997     1.000
```

**四路彼此相关 0.986–0.998，且每一路与源相关 0.90–0.95。**
它们不是四个不同乐器，而是**同一段内容的四次近似重建** —— `track` 参数几乎不起作用。
四路相加得到 **-1.92 dBFS、峰值 4.000**（源是 -11.26 dBFS），即同一份内容被复制了四遍。

纯白噪声对照（无任何乐器结构）：

| 抽取目标 | 输出 RMS | vs 源相关 |
|---|---|---|
| noise → drums | -16.33 dBFS（源 -16.48） | **+0.114** |
| noise → guitar | -16.15 dBFS | **+0.060** |

从白噪声里"抽出"了鼓和吉他，能量与源几乎相同。**没有任何内容可供分离，它仍然输出了东西。**

## 三、真分离的必要条件：分轨相加必须重建原曲

对用户真实工程 `p_7atqcqig` 的全部分轨做单位增益相加：

```
--- 5 条乐器轨（排除 DC 坏掉的人声）
  原曲    RMS -15.55 dBFS  peak 1.000
  相加    RMS  -6.08 dBFS  peak 3.222      ← 已经爆表
  残差    RMS  -7.09 dBFS  → 比原曲还高 +8.47 dB
  波形相关 +0.477                          ← 真分离应 ≈1.000
  频段(相加/原曲) low 14.8/9.5  lowmid 37.0/14.1  mid 22.6/29.4  himid 18.4/31.2  high 6.5/15.6

--- 6 条全部（含人声）
  相加    RMS  -1.69 dBFS  peak 3.936
  残差    比原曲高 +13.51 dB
  波形相关 +0.475
```

**相加之后残差比原曲本身还响**（+8.47 / +13.51 dB）、波形相关只有 0.475、
中频缺 22.6/29.4、中高频缺 18.4/31.2。这是"四份互不对齐的近似物叠在一起"的典型特征，
不是分解。

> 与纯钢琴实验对比：纯钢琴源的 4 路分轨彼此相关 0.99，说明**当源内容单一时，
> 它会把同一内容重复输出**；真实混音内容复杂时，各次重建的"编造内容"不同，
> 于是彼此相关降低（0.005–0.855）、相加更不可能还原。
> 两种情况指向同一个结论：**输出由"源 + 提示"重新生成，不由源分解而来。**

## 四、那"糊"是怎么来的（为什么不是调参能解决）

- 每条分轨都是**独立的一次完整重合成**，相位与源无关 → 相加必然不相干、必然削顶
- 每次重合成都会**丢掉源里它"不理解"的那部分频谱**，并**补上它"以为"该有的部分**
  → 中频/中高频出现结构性缺口（实测 mid -14.1pp、himid -16.6pp）
- 分轨之间还共享一个低频床（两两相关低到 0.005、高到 0.855 不等），
  所以叠加时低频堆叠、中高频互相抵消
- **增益是线性的，无法改变频段占比**（已实测：修复前后频段分布完全相同）

所以上一轮我只把「叠加削顶」修掉了（峰值 3.149 → 0.525、削顶 11.21% → 0.00%），
**没有也不可能修好分离度**。这一点当时已写进代码注释和 UI 文案。

## 五、结论与建议

### 结论
**ACE-Step 的 `extract` 不是分轨工具。** 它没有分离网络，只有"按指令重合成"。
任何参数调优（步数、guidance、seed、caption、arm 名）都无法让它变成真分离，
因为**问题不在参数，在任务定义**。

### 产品层面应当怎么处理

1. **诚实定位（必要）**：把界面上的「生成分轨 Stem」明确标注为
   **「AI 重编分轨（近似重合成）」**，而不是"分离/拆轨"。
   当前 UI 文案已有"分轨是分别重合成的，不是原曲的严格分解"，
   但标题与入口仍叫"分轨 Stem"，容易让用户按"分离"预期使用。建议改入口文案。

2. **要真正的分轨，必须换模型**。业界标准做法是专用的 **source separation** 模型：
   - `Demucs`（htdemucs / htdemucs_ft，MIT）—— 4 轨（鼓/贝斯/人声/其他），
     或 6 轨变体；CPU 可跑，GPU 极快；有 ONNX 导出路径，可像现在这样打包成本地运行时
   - `MDX-Net` / `UVR` 系列 —— 质量更强，但授权与分发需逐个确认
   - `Spleeter`（MIT，但需 TF，较老，质量落后于 Demucs）
   这些都是**真分离**：各轨相加接近原曲（波形相关通常 >0.95），
   而且支持"只取某几轨"（例如人声/伴奏）。

3. **架构上如何接入**（无需推翻现有设计）：
   - 现有 Companion 已有一套「任务类型 → 模型变体」派单与落轨链路
   - 新增任务类型 `separate_stem`（区别于 `generate_stem`），
     派给一个 Python 侧 Demucs worker（与现有 ace-server 并列的第二种 executor）
   - 落轨链路、增益分级、默认静音、护栏都可以复用
   - 关键收益：分离出的各轨**相加能还原原曲**，用户"mute 掉整曲只听分轨"才有意义

4. **短期降级方案（若不引入新模型）**：
   - 保留现有功能但明确定位为"AI 重编/加轨"，不要作为"分轨"售卖
   - 或直接下架分轨入口，避免用户按"分离"预期反复踩坑

## 六、本轮未做的事

- **没有引入任何新模型**。是否引入 Demucs 属于产品与授权决策，需要你确认
  （下载体积约 300MB–2GB、需要 Python+torch 运行时或 ONNX 运行时、
   与现有"纯 C++ 运行时 + GGUF"的打包策略不同）。
- **没有改代码**。本轮只做归因验证，避免在结论确认前扩大改动。
