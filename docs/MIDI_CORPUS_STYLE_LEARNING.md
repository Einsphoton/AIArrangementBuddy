# MIDI 语料采集与风格学习（可行性评估与实施方案）

> 问题：能不能写爬虫在网上按指定风格搜集大量 MIDI，再「学习」这些语料，用来强化 AI 生成的曲风与质量？
>
> 本文给出结论、边界、可落地的三层方案、与现有代码的接入点、评估方式与分阶段路线。
> 相关代码：`packages/core/src/generators/`（规则生成器）、`packages/core/src/arrange.ts`（编曲器）、
> `apps/server/src/tools/`（Agent 工具）、`apps/server/src/agent/quality.ts`（生成后质量自检）。

---

## 0. 一句话结论

**能做，但爬虫是最不值钱的一环，而且它只解决「符号层」的问题。**

- 用 MIDI 语料提升 AI 编曲的水平：**明确可行**，且有三条成本差 10 倍的路径（统计先验 → 检索增强 → 微调模型）。
- 用 MIDI 语料提升「音色 / 混音 / 演唱 / 母带」的听感：**完全无效**，那是音频域的事。
- 「网上爬 MIDI」的边际价值，**只体现在公开数据集覆盖不到的流派**上；主流风格（流行 / 摇滚 / 爵士 / 电子 / 古典）已经有现成的、许可清晰的几十万条数据，先写爬虫属于把 80% 的时间花在 20% 的收益上。

如果只能记住一条：**先做「风格先验 + 候选重排」，不要一上来就训模型。**

## 1. 先把「质量太差、不好听」拆开

「不好听」至少分布在四个层，语料能不能帮上忙完全不同：

| 层 | 具体病症 | MIDI 语料是否有用 |
| --- | --- | --- |
| **符号层**：音符 / 和声 / 编曲 | 平行五八度、动机不发展、和声原地踏步、密度失衡、音区打架、配器没层次、段落没有起伏、到处都是「正确但无聊」的四分音符 | ✅ **直接有用**，这是本项目的主要目标 |
| **演奏层**：力度 / 时值 / 人性化 | 全部等力度、机械量化、每个音都踩在格子上，听起来像音源 demo | ✅ **见效最快**（见第 6 节） |
| **音色 / 混音层** | 音色廉价、频段打架、没有空间感、动态压缩过度 | ❌ 需要音频样本 / 混音工程，不是 MIDI |
| **音频纹理层**：演唱 / 声码 / 噪音 | Suno、Udio、MusicGen 这类音频模型的短板 | ❌ **MIDI 一点用都没有**（见 2.1） |

> 这就是第一个必须先回答的问题：你说的「AI 生成的音乐」如果是 Suno / Udio / MusicGen 这类**音频模型**，那么 MIDI 语料无法直接喂给它，只能走「先生成 MIDI 编曲 → 用你的工坊做音源渲染」这条曲线救国的路。如果指的是本项目的 AI 编曲 Agent（`apps/server/src/agent/`），那 MIDI 语料正中靶心。

## 2. 三条必须接受的现实边界

### 2.1 音频模型不吃 MIDI

Suno / Udio / MusicGen 的训练数据是音频波形（或音频 codec token）。MIDI 在它们眼里只是一串「谁在什么时候按了哪个键」，没有音色、没有混响、没有演唱。往这类模型上「灌 MIDI」在工程上不成立。

可行的组合是：**MIDI 层负责「写得好」，音源 / 音频模型负责「听着好」**。本项目本身就是这个形状（`packages/core` 产出 MIDI → `apps/web/src/audio/` 用 SoundFont / 合成器渲染），所以 MIDI 语料的收益会直接体现在编曲结构上。

### 2.2 语料的真瓶颈是「干净且合法」，不是「抓不到」

网上 MIDI 的典型分布：

- 大量是**别人对版权作品的转录 / 扒带**（流行歌、动漫、游戏 BGM），法律上属于衍生物；
- 质量高度参差：错拍、tempo map 乱写、把和弦切成 40 条单音轨、没有力度、过度量化、鼓组映射到不存在的音符、GM 音色号全错；
- 真正「干净、多轨、有力度、编曲完整」的 MIDI 是稀缺品，**这恰恰是学术数据集存在的理由**。

### 2.3 「从零训练」在小数据上一定不好听

符号音乐生成不是 LLM 那种「喂几万条就能涌现」。一个 20 万条 MIDI 的数据集，对 Transformer 来说仍然是**小数据**：从零训练出来的模型会产出「语法正确、语义空洞」的音符——比现在的规则生成器更糟，因为规则生成器至少有和声约束。

**能听出提升的做法是：先验（统计）+ 检索（示例）+ 重排（选择）。** 训练模型是可选项，不是第一步。

### 2.4 关于「真正的学习 / 涌现」：把话说清楚

「让 AI 真正学会这四种风格，然后涌现出高质量的原创」——这句话里有两件事，一件有据可依，一件没有公开证据。

**做不到的（不要信任何声称做到的方案）**：

- 没有公开论文证明**小规模**符号模型（<1e8 参数、<1e5 曲目）能产出训练集里不存在的**风格组合**并保持质量。
- 现有最好结果的规模是：MIDI-GPT 训练于 GigaMIDI（>100 万 MIDI），NotaGen 用 160 万份 ABC 预训练后只用 9K 古典微调。也就是说，「像样」的门槛在**百万级语料 + LLM 级参数**，不是几千首。
- 「涌现」在 LLM 上是规模带来的能力跳变；音乐里没有对应的免费午餐。几千首 MIDI 训出来的模型不会涌现，只会**收敛到平均**——听感上是「哪首都像，哪首都记不住」。
- 而且已有实证：符号模型存在**motif 级局部过拟合**（高频动机更容易被原样吐出来），这是「原创性」的直接威胁，需要用移调增强、label smoothing、Top-K、记忆化检测等手段压制。

**能做得到的（这才叫「真学习」）**：

1. **学到可计算的文化先验**：和弦进行的条件概率、织体的音区/密度分布、乐句重复率、律动偏移分布——这些能用几千首统计出来，并且**确实是从数据里学到的，不是人写的规则**。
2. **组合泛化**：「A 风格的和声进行 × B 风格的配器 × C 风格的律动」这种横向组合，用**检索 + 重组**（而不是梯度训练）可以达到，而且质量可控、可解释、可回滚。
3. **判别式学习**：训一个「像不像这个风格」的评分器（几千条数据足够），用它从 N 个候选里挑最好的。这是**训练**，也是**学习**，而且是能直接提升听感的一步。

> 一句话：**「学习」可以实现，「涌现」不能承诺。** 但对「写出风格对、有原创感的东西」这个目标，前三条已经够了——人类作曲家写出新歌，靠的也主要是先验 + 重组，而不是凭空涌现。

## 3. 先别写爬虫：现成语料清单

| 数据集 | 规模 | 内容 | 能否按目标风格筛 | 适合做什么 |
| --- | --- | --- | --- | --- |
| **[GigaMIDI](https://github.com/Metacreation-Lab/GigaMIDI-Dataset)** | **> 100 万 MIDI** | MetaMIDI 的超集，带 Discogs / Tagtraum / Last.fm 三套标签 | ✅ **唯一有希望的起点**：Discogs 有 J-Rock、Britpop、Post-Hardcore、Video Game Music 等 style 标签 | 四类风格的弱标签粗筛 → 人工听检 |
| **MetaMIDI** | 436,631 | 全流派，1500 万条元数据 | ⚠️ genre 只覆盖 33% | 覆盖面广，但标签稀疏 |
| **Lakh MIDI**（LMD / LMD-clean） | 176,581（45,129 对齐 MSD） | 对齐 Million Song Dataset | ❌ 只有 MSD 粗标签，无 J-rock/Britpop 细分 | 通用风格先验、和弦进行 |
| **[NES-MDB](https://github.com/chrisdonahue/nesmdb)** | 5,278 首 / 397 款 NES 游戏 | NES 音乐符号化（含 FF/DQ 早期曲目） | ✅ 按游戏/厂商 | **JRPG 早期语汇**（chiptune，非管弦配乐） |
| **[VGMIDI](https://github.com/lucasnfe/vgmidi)** | vgmusic 钢琴改编 | 带情感标签的游戏钢琴曲 | ✅ 按游戏 | JRPG 和声与动机（只有钢琴编配） |
| **Slakh2100** | 2,100 首多轨 | 每轨独立 + 合成音频，编曲结构干净 | ❌ 无 genre | **编曲/配器**分析（谁和谁一起出现） |
| **MAESTRO v3** | 1,276 场 / 198.7 小时 | 演奏级钢琴 MIDI + 音频 | ❌ 仅作曲家 | **演奏层**人性化、力度曲线 |
| **[Groove MIDI (GMD)](https://magenta.withgoogle.com/datasets/groove)** | 1,150 文件 / 13.6 小时 | 真鼓手演奏 | ⚠️ 18 种鼓风格，只有 rock/punk | **律动、swing、ghost note** |
| **MidiCaps** | ~168k（源自 Lakh） | 自动生成的文本描述 | ⚠️ 弱标签 | 文本 → 风格检索 |
| **POP909 / EMOPIA** | 909 / 387 首 | 华语流行、情感标注 | ❌ | 和声进行、段落结构参考 |
| **JSB Chorales / music21 语料** | ~371 首四声部 | 教科书级声部进行 | ❌ | **声部进行规则**的黄金标准 |

**未找到公开数据集**：J-rock / J-pop 多轨 MIDI；JRPG OST 多轨 MIDI。这两类只能靠「弱标签粗筛 + 人工听检 + 自建转录」补——**这也正是你想写爬虫的直觉来源，这个直觉是对的，只是执行方式要换。**

**结论：**
1. 有 GigaMIDI 之后，**前三种风格（J-rock / Britpop / Post-Hardcore）不需要从零爬虫**——先下载 GigaMIDI，按标签粗筛，人工听检 200 首做金标，比写爬虫快一个数量级。
2. 只有 **JRPG 配乐**是真正的数据洼地：官方只有音频，网上 MIDI 绝大多数是**钢琴独奏改编**（`noDrums` 标签会告诉你比例），学不到配器。这一块必须走「音源转录 + 人工精修 + 少量高质量多轨扒带」的组合。
3. 爬虫的正当用途因此收敛为一个：**补齐 GigaMIDI 覆盖不到的 JRPG / 日系同人转录**，且只做本地研究、不入库不出库。

## 3.5 你这四类风格：可形式化的特征 + 语料打法

四类风格的共同点，恰好也是本项目当前生成器最缺的东西：

> **乐队编制（吉他/贝斯/鼓为主体）+ 强动机旋律 + 段落级动态对比（主歌/副歌/大副歌）。**
> 现在 `packages/core` 的生成器是「4~8 小节循环 + 8 个风格预设」，**没有段落概念，也没有动机概念**。
> 这比「缺语料」更根本 —— 语料能教你「和弦怎么写、织体多密」，教不了你「结构怎么搭」。

| 风格 | 可形式化的核心特征 | 语料打法 | 主要难点 |
| --- | --- | --- | --- |
| **日摇**（STRAIGHTENER / AKG） | 王道进行 `IV-V-iii-vi` 与小室进行 `vi-IV-V-I` 的高频出现；大调为主但频繁借用 `bVII`、`III`；`add9`/`sus4` 挂留；160–200 BPM 的八分吉他扫弦；贝斯八分走根音；副歌前 dropout（全乐器停半拍）；吉他间奏 | GigaMIDI 按 Discogs `J-Rock` 粗筛 → 人工听检 100~200 首 → 建 profile | 标签覆盖率低，需要人工金标；**唱腔与人声旋律不在 MIDI 里** |
| **英伦摇滚**（Muse / Coldplay） | `add9`/`sus2`/`sus4` 与平行和弦；Mixolydian 的 `bVII`；钢琴 ostinato + 失真吉他反差；Muse 常用 5/4、7/8 与半音下行贝斯；Coldplay 用 IV–I–V–vi 的明亮大调 + 后段 orchestral build | 同 GigaMIDI（`Britpop` / `Alternative Rock`），再加 Slakh 学**配器层次** | 「高级感」来自编曲留白与音色，MIDI 只能给结构 |
| **美式 Hardcore / Alt-rock**（30STM） | 强力和弦（root+5）与 drop-D 开放弦；小调 `i–bVI–bIII–bVII`；双踩与军鼓连打；副歌大合唱（多层人声叠录）；合成器铺底混在失真墙里；**quiet verse → huge chorus** 的动态落差 | GigaMIDI（`Post-Hardcore` / `Alternative Metal`）+ GMD（学律动与 ghost note） | 力度与动态层次是听感核心，需要**演奏层**（第 6 节），纯音符统计抓不住 |
| **JRPG 配乐**（植松 / 光田 / 菊田 / 門倉） | 调式交替 `bVI`/`bVII`/`bIII`、`IV→iv` 借用、半音中音关系（C→Ab）、副属和弦；16 分琶音 ostinato；弦乐铺底 + 铜管 fanfare + 合唱 + 竖琴；**动机主导**（短动机 + 模进 + 变奏）；32~64 小节 loop 曲式；光田常用 3/4、6/8、5/4 | NES-MDB（早期曲目）+ VGMIDI（和声/动机）+ 自建多轨转录（补配器） | **多轨语料几乎不存在**；粉丝转录 90% 是钢琴独奏（`noDrums` 会告诉你） |

### 这张表怎么用

1. **先做 JRPG 之外的三类**：GigaMIDI 能筛，两三天就能出第一批 profile。
2. **JRPG 单独当项目**：它的价值最高（你的核心审美），但语料最差。建议路线是
   「NES-MDB 学声部预算 + VGMIDI 学动机与和声 + 自建 20~50 首多轨精修金标」。
   20~50 首听起来少，但对**动机与配器**这种结构性问题，金标的质量远比数量重要。
3. **每类都先跑一遍 `pnpm corpus:profile`**，用 `corpus.tags` 里的 `noDrums` / `robotVelocity` 比例
   判断这批语料能不能用 —— 这个数字通常比你的直觉悲观。

## 4. 如果确实要写爬虫

### 4.0 先算一笔账：全网到底有多少 MIDI 可爬（2026-11 实测，含更正）

| 站点 | 实测 | robots 状态 | 能否批量取文件 |
| --- | --- | --- | --- |
| VGMusic（全站） | **> 30,000**（SNES 6,708 / NES 4,204 / Genesis 2,413 / PS2 832） | 无 robots（404） | ✅ **可以** |
| **BitMidi** | **113,229** 条 MIDI | `Disallow: /uploads/`，而下载链接恰好全在 `/uploads/` | ⛔ **文件被禁**，只能抓元数据或找站方授权 |
| MidiShrine | 未统计 | `Disallow: /` | ⛔ **明确禁止** |
| Songsterr | — | robots 返回 403 | ⛔ **拒绝机器人**，且无文件可下 |
| Ultimate Guitar | — | ToS 禁止抓取、下载需登录 | ⛔ **不爬**；改成「自己下 GP → 本地转换」 |
| 其他（freemidi / kunstderfuge / ichigos） | 数千 ~ 万级 | 多数允许 | ⚠️ 需逐站写适配器（页面无直链 `.mid`） |

**更正**：本文早先写「全球游戏 MIDI 存量大概 3~6 万」，那是**游戏类**的数字。
加上 BitMidi（11.3 万，流行/摇滚为主）之后，全网**可抓取**的 MIDI 元数据规模是 15 万级，
但**能合法批量下载文件**的只有 VGMusic 一家（3 万）。这是两个不同的数字，别混。

再拆到你的四类目标：

| 目标 | 可批量获取的量级 | 能直接进语料的比例 |
| --- | --- | --- |
| JRPG 配乐 | VGMusic 3 万里的一个子集，**几千** | ~10~20%（大量是钢琴单轨改编） |
| 日摇（STRAIGHTENER / AKG） | 免费站基本关闭，**百 ~ 千级** | 低，多为单轨旋律 |
| 英伦摇滚（Muse / Coldplay） | 同上；西方以 Guitar Pro 为主 | 需 `convert-gp.mjs` 转换（已实现并验证） |
| 美式 Hardcore（30STM） | 百级 | 同上 |

**结论：**
1. 「几十万条 MIDI」= **GigaMIDI（210 万，但需申请访问，不是直接下载）**，不是爬虫能给的东西。
2. 爬虫的现实产出是 **1~3 万**（以 VGMusic 为主），定位是「补 JRPG 曲目 + 元数据」。
3. 日摇/英伦/Hardcore 这三类，**Guitar Pro 转换比爬虫靠谱**——那些 tab 站本来就不是 MIDI。
4. 别按「几十万」定 KPI。按「每风格 500~2000 首、能通过质量闸门」定，更接近实际。

### 4.1 站点筛选：先建白名单，再写代码

优先级从高到低：

1. **公有领域 / CC 明确标注**的乐谱与 MIDI 站（古典、民谣、传统曲目）；
2. **自建 / 用户上传且授权**的来源（自有素材、合作曲库）；
3. **有明确 API 与条款**的曲库（付费也要比打官司便宜）；
4. 其余站点：只抓**元数据与统计**，不抓文件本体。

给每个站点记录：`site / 条款链接 / 允许抓取范围 / 速率上限 / 是否允许存储原始文件`。**这个台账是唯一能证明「数据来源可追溯」的东西，必须落库。**

### 4.2 法律与合规底线（务必写进代码注释，不只是文档）

- 多数网站 MIDI 是**他人对版权作品的转录**，抓取 + 存储 + 训练 + 再分发，是四个不同层级的风险，**不要打包默认都做**；
- 原始文件**不入 git、不进 Docker 镜像、不随产品分发**；只保留「派生的统计特征 + 来源元数据」；
- 训练产物若可能「复现」某首具体作品（例如模型能吐出原曲旋律），属于实质性相似风险，需要做**记忆化检测**（见 9.3）;
- 商业发布前，训练数据的许可链条要能讲清楚；不确定就换数据集，别赌。

**两个法域的具体边界（本项目只做本地研究，这一条决定你安不安全）：**

- **日本**：著作権法第 30 条之 4 允许以「情報解析」为目的的复制与改编，**但附有但书**——「著作权人利益会被不当损害」的情形不适用；且单纯「欣赏作品表达」的目的不在该条范围内。文化庁 2024-03-15 发布《AI と著作権に関する考え方について》为官方解释。**本地分析、训练属情報解析，风险低；把语料做成可欣赏的数据库则可能越界。**
- **中国**：《著作权法》第 24 条列举的合理使用（含个人学习、研究、欣赏）**没有**机器学习/训练的专门条款；《生成式人工智能服务管理暂行办法》第 7 条要求训练数据「使用具有合法来源的数据和基础模型」。**本地研究可依第 24 条个案主张，商业化则没有明确豁免。**

### 4.3 抓取工程要点（如果做）

| 要点 | 做法 |
| --- | --- |
| 礼貌 | 读 `robots.txt`、单站点 ≤1 req/s、固定 UA、遵守 `Crawl-delay` |
| 增量 | URL 指纹（`sha1(url)`）+ ETag/Last-Modified 落库，重跑只抓变动 |
| 断点 | 队列持久化（SQLite 即可），随时可停可续 |
| 去重 | 音符级指纹：`(round(onset/量化格), pitch, dur)` 序列哈希；同名不同编曲要保留 |
| 质量控制 | 见 4.4 |
| 存储 | `data/corpus/<source>/<sha1>.mid` + `index.jsonl`（来源、许可、抓取时间、特征摘要） |

### 4.4 质量闸门（八道，缺一不可）

1. 解析失败 / 0 音符 / 单音轨无力度 → 丢弃；
2. 有效长度 < 8 小节 → 丢弃（除非专门收 loop 素材）；
3. 量化误差过大（音符起点偏离 1/16 网格 > 40%）→ 标 suspicious，不进训练只用统计；
4. 音域越界（<21 或 >108）、音符重叠同音（重叠 > 50% 时值）→ 清洗；
5. 每轨音符数 < 4 的「幽灵轨」→ 合并或删除；
6. 无力度方差（全 100）→ 标记 `quantized_robot`，**不能用于演奏层学习**；
7. 打击乐轨映射到 GM 之外 → 重映射或丢弃；
8. 时值巨长（> 32 拍单音）、tempo 极端（< 20 或 > 300）→ 丢弃。

### 4.5 规范化管线（比爬虫重要 10 倍）

```
原始 .mid
  → 解析（PPQ 统一 / tempo map 化简 / 拍号与调性检测）
  → 轨拆分与角色识别（旋律 / 和声 / 低音 / 鼓 / 铺底）
  → GM 音色映射与修正
  → 小节对齐、切分为 4/8 小节乐句
  → 特征提取 → 风格画像（style profile）
```

「角色识别」是编曲类分析的核心：它决定你能不能说清「这个风格里，铺底一般比贝斯高几个八度、多久出现一次」。

## 5. 「学习」的三层路线（按 ROI 排序）

### L1 风格先验（不训练任何模型）— 1~2 周，收益最大

从语料里抽**可解释的统计量**，直接替换生成器里现在硬编码的常数。

产出物：每个风格一张 `style-profile.json`

```jsonc
{
  "style": "jazz",
  "tempo": { "median": 132, "p10": 96, "p90": 200 },
  "keys": [{ "key": 7, "share": 0.18 }],
  "chords": {
    "vocab": ["ii7", "V7", "Imaj7", "vi7", "bVII7"],
    "bigrams": { "ii7>V7": 0.41, "V7>Imaj7": 0.33 },
    "perBarChanges": 1.8
  },
  "texture": {
    "densityPerBar": { "chords": 6.2, "bass": 3.9, "pad": 8.1 },
    "voicingSpreadSemitones": { "chords": [7, 19], "pad": [12, 31] },
    "doublingRate": 0.34
  },
  "drums": { "ghostNoteRate": 0.22, "swingRatio": 0.62, "kickPatterns": [...] },
  "dynamics": { "velocityMedian": 82, "velocityStd": 14, "accentOnBeat1": 1.18 },
  "form": { "phraseLenBars": 4, "sectionRepeatRate": 0.55 }
}
```

**接入方式**：

- `packages/core/src/generators/index.ts`：`STYLE_PROGRESSIONS`、`GROOVES`、`STYLE_GROOVE`、各 `kind` 的密度与音域常数，全部改为「从 profile 采样」（保留现有常量作为 fallback，保证不退化）；
- `apps/server/src/agent/prompt.ts`：把 profile 渲染成一段**风格卡**注入系统提示（「jazz 的和弦变化频率约 1.8 次/小节，铺底音区在 C3–G4」），让 LLM 在选工具参数时有具体锚点；
- 这是**纯加法**，不改架构、不引入 Python、不需要 GPU。

预期：风格「像不像」进步明显；「好不好听」进步中等（因为结构问题还在）。

### L2 检索增强（RAG over MIDI）— 2~4 周，性价比第二

#### 先把术语对齐（这三种东西经常被混为一谈）

| 说法 | 实际是什么 | 改不改模型权重 | 能不能产生新能力 |
| --- | --- | --- | --- |
| **RAG**（检索增强生成） | 写之前先去库里查资料，把查到的真实片段塞进上下文 | ❌ | ❌ |
| **Skill**（Agent 领域的说法） | 一份 markdown 工作流说明书，模型按它一步步做 | ❌ | ❌ |
| **In-context learning / few-shot** | 在提示里给几个例子，模型照着模仿 | ❌ | ❌ |
| **微调 / 训练** | 改权重 | ✅ | ✅（但要规模） |

**结论：RAG + Skill 确实能带来「学习」的效果，但那是「开卷考试」——翻书能提分，翻书不会让你长出新的脑子。**
它能让你拿到风格的「像」和「稳」，拿不到「涌现」。原因见 §2.4。

#### 为什么音乐上 RAG 特别有效，又为什么单靠它一定失败

- **有效**：LLM 脑子里关于「日摇」的知识是**文字描述**（"失真吉他、快节奏、副歌大跳"），缺的是具体音符。RAG 补的正是这个空白——给它看真实的日摇小片段，它立刻能模仿得很像。
- **失败**：LLM 输出音符的**保真度**极差。4 小节 8 轨约 500 个数字（音高/起点/时值/力度），token 生成会崩：时值对不上、声部打架、拍子漂移。代码有编译器兜底，音符没有。
- **所以绝不能让 LLM 直接写音符。** 现在 `apps/server/src/tools/` 里的 `write_notes` 就是让模型直接写音符——这是当前质量天花板的主要来源之一。

#### 正确架构：LLM 当指挥，不当抄谱员

```
① 检索层   search_style_reference(style, chords, emotion) → 3~5 个真实片段摘要 + 风格画像
② 规划层   LLM 只输出结构化意图 JSON（**不含任何音符**）：
           { 曲式: [intro, A, B, A', B'],
             每段: { 和弦进行, 织体选择, 密度, 配器, 动机编号 },
             动机: { 音程轮廓, 节奏型, 变形计划(模进/倒影/扩缩) } }
③ 实现层   packages/core 生成器把意图渲染成音符（profile 采样参数 + 乐理约束）
④ 判别层   styleScore 打分 → 多候选重排 → 取最优
```

**关键点：第 ② 层输出里不能有音符。** 模型擅长「选和弦、定结构、挑织体、编动机」，不擅长「算第 37 拍那个音的时值」。把不擅长的部分交还给确定性代码，是这套架构的全部价值。

#### 接入方式

- 新增 Agent 工具 `search_reference(style, chords, emotion, instrumentation, k)`，返回 3~5 个片段的**文本化描述 + 音符摘要**（不返回原始文件）；
- 把 `write_notes` 从「主路径」降级为「微调工具」：主路径改成 `apply_arrangement_plan(plan)`，由生成器落地；
- 风格画像（L1 产物）随系统提示注入，作为「风格卡」。

#### 成本与上限

| 方案 | 上线时间 | 需要 GPU | 质量上限 | 风险 |
| --- | --- | --- | --- | --- |
| RAG + Skill + 生成器参数化 | 1~2 周 | ❌ | 风格贴合度大提升，结构不变 | 低 |
| ＋检索重组（片段拼接 / 变奏） | +2~4 周 | ❌ | 织体明显丰富 | 中 |
| ＋判别器重排 | +1~2 周 | ❌ | 干掉大部分「难听」候选 | 低 |
| LoRA 微调符号模型 | 1~3 月 | ✅ | 需百万级语料才像样 | 高 |

**你要的「挂一层上去」的方案存在，而且是最优路径的第一步；但它提升的是「像」和「稳」，不是「涌现」。**

### L3 模型微调 / 训练 — 1~3 个月，可选，且要 GPU

如果 L1+L2 还不够，再考虑：

| 路线 | 数据需求 | 算力 | 风险 |
| --- | --- | --- | --- |
| LoRA 微调现成符号模型（Anticipatory Music Transformer / MIDI-GPT / NotaGen 类） | 5k~50k 条同风格 | 单卡 24~48G 可起步 | 输出不稳定、需要强后处理与约束解码 |
| 从零训小型 Transformer（4~8 层，条件生成） | 20k+ 条 | 单卡够 | 「语法正确但空洞」，大概率打不过 L1+L2 |
| 训练**重排器**（而不是生成器） | 偏好对 / 质量标注 1k~10k | 极低，CPU 都能跑 | 最低风险，见第 7 节 |

**参考尺度（已核实的公开结果，用来校准你的预期）**：

| 模型 | 训练规模 | 结论 |
| --- | --- | --- |
| MIDI-GPT（AAAI'25） | GigaMIDI，**>100 万** MIDI | 主结论是「不复制训练材料 + 风格相似 + 属性可控」，**没有 MOS 主观分** |
| NotaGen（IJCAI'25） | **160 万**份 ABC 预训练 + **9K** 古典微调 + DPO | A/B 优于基线，但**仅古典钢琴谱** |
| Anticipatory Music Transformer | Lakh MIDI，≤ 1.28 亿参数 | 20 秒片段人评「伴奏音乐性与人类相当」 |

也就是说：**做到了「风格相似且不逐音抄袭」的门槛在百万级语料 + 上亿参数**；「组合泛化」目前没有公开证据。
本项目手头的量级（几千到几万首）适合做微调与重排，**不适合做梦**。

> 微调模型最现实的价值是**补风格**（新流派、民族乐器语汇），而不是「提升通用编曲水平」。通用水平的提升，靠的是先验、检索和约束。

## 6. 最被低估的一层：演奏层（力度 / 时值 / 微时序）

这一层是**投入产出比最高的**，而且完全不需要训练：

- 从 MAESTRO / Groove MIDI 抽「**力度分布 + 时值微偏差 + 强拍重音 + swing 比例**」；
- 生成后在 `packages/core` 里加一个**人性化后处理**：按风格 profile 抖动 velocity（±σ）、把八分音符按 swing ratio 偏移、给强拍加权、给旋律轨加 ±8ms 的时序偏差；
- 听起来「像人弹的」而不是「像音源 demo」——这是同一堆音符听感差异最大的一项。

现有代码里已经有「人性化」入口（钢琴卷帘的 humanize 命令），把它从「±固定值随机」升级为「按风格采样分布」，是一个几十行改动的任务。

## 7. 「强化学习」怎么落地才现实

你说的「学习 / 强化」如果指 RLHF，直接对 LLM 做强化学习**成本极高、收益不可控**（奖励信号是音乐质量，本身就难以定义）。现实的做法是把它拆成三个阶段，每一阶段都可以独立验收：

### 阶段 A：多候选 + 可解释评分 + 重排（不需要训练）

```
Agent 生成 1 份工程
   ↓ （扩展到 4~8 份候选：不同 seed / 不同织体 / 不同密度）
规则评分器 styleScore(project, profile)
   ↓ 硬伤直接淘汰（复用 quality.ts 的思路），软指标加权
选 top-1 给用户（或让用户 A/B 挑）
```

评分维度（都可解释、都可调权重）：

| 维度 | 指标 |
| --- | --- |
| 和声 | 调外音比例、和弦音覆盖率、平行五八度数、和声变化频率偏离 |
| 声部 | 声部交叉率、音域越界率、间距分布偏离 |
| 节奏 | 节奏 n-gram 在语料中的覆盖率、密度偏离、网格机械度 |
| 织体 | 同质化程度（每小节音型重复率）、配器组合在语料中的常见度 |
| 形式 | 段落长度分布、重复/变化比例、是否有高潮点 |
| 演奏 | 力度方差、时序偏差匹配度 |

### 阶段 B：从偏好数据训一个重排器（低风险）

- 用户在界面上做 A/B 选择（「这个更好听」），数据落库；
- 用这些偏好对训一个**小模型 / 特征加权**做 reranker；
- 这就是标准的 preference-based learning，但**不碰生成器本体**，出问题随时能回滚。

### 阶段 C：DPO 微调（可选项）

- 用阶段 B 的偏好对做 DPO，微调一个小的符号模型或 pattern 生成模型；
- 只有在 A/B 达到每周数百次有效偏好、且 L1+L2 已封顶时才值得做。

## 9. 评估：别用耳朵当唯一裁判

### 9.1 客观指标（生成 vs 语料分布）

- 音级直方图的 JS 散度；
- 音程直方图（含大跳比例）；
- 节奏 n-gram 覆盖率；
- 每小节事件数分布（密度）；
- 声部交叉率、平行五八度率；
- 同质化：相邻小节音型重复率；
- 演奏层：velocity 分布、时值偏差分布。

### 9.2 主观盲测

- 同 prompt 生成 20 组，A/B 盲测（不告诉听者哪个是改前/改后），记录偏好率；
- 目标：偏好率 > 60% 才算「有提升」；< 55% 视为噪声。

### 9.3 记忆化检测（如果做了 L3）

- 检查生成片段与训练语料的 n-gram 重合度；过高说明模型在背谱，需要加正则 / 削温度。

## 12. 已定的前提（2026-11 更新）

| 问题 | 结论 |
| --- | --- |
| 目标风格 | **日摇**（STRAIGHTENER / ASIAN KUNG-FU GENERATION）、**英伦摇滚**（Muse / Coldplay）、**美式 Hardcore**（30 Seconds to Mars）、**JRPG 配乐**（植松伸夫 / 光田康典 / 菊田裕树 / 門倉聡） |
| 提升对象 | 本项目的编曲 Agent，**仅限 MIDI 范围**（不涉及音频/音色/混音） |
| 法律边界 | **只做本地研究与学习**，不分发、不商用 |

仍待决定（进入 P2 之前需要）：

1. **有没有 GPU / 愿不愿意租**？决定 P4（LoRA 微调）是否存在。
2. **能不能接受人工听检成本**？四类风格的标签质量都不高，要建金标就得自己听。按 200 首 / 每首 1 分钟估算，约 4~6 小时。
3. **JRPG 多轨金标谁来听写**？如果没有人愿意精修 20~50 首多轨，JRPG 这一档就只能停在「和声 + 动机」层面，配器学不到。

## 13. 本仓库已落地的工具

P0 的「语料底座」已经实现，零依赖、纯 Node、不碰 `packages/core`：

```
scripts/corpus/
  midi-read.mjs    零依赖 SMF 解析（format 0/1/2、running status、tempo map、拍号、调号）
  features.mjs     特征提取（调性/和弦/音程/律动/角色/力度/连断/重复度）+ 质量闸门
  profile.mjs      聚合成分位数画像；CLI：inspect / build
  selftest.mjs     合成 MIDI 全链路自检（23 项断言，离线可跑）
  README.md        用法、数据来源、标签含义、法律边界
```

```bash
pnpm corpus:selftest                                        # 离线自检
pnpm corpus:inspect data/corpus/jrpg/nes-mdb/foo.mid        # 单曲特征

```

画像结构见 `scripts/corpus/README.md`，核心字段：
`tempo / timeSignature / key / rhythm(密度·反拍率·网格偏离·swing) / harmony(变化率·调内率·功能进行) / intervals / texture(角色占比·各角色音区与密度) / dynamics / articulation / repetition`。
