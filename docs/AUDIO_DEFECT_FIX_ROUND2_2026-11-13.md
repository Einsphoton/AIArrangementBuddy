## 1. 缺陷 ①：人声轨是 DC + 噪声（硬 bug）

### 诊断
用户工程里 7 条轨逐条测 DC 偏置：

```
轨名                 DC偏置     DC能量占比    总RMS   去DC后RMS
生成 · J-ROCK…      +0.0018      0.01%   -15.55    -15.55
Stem · 人声         +0.6367     99.71%    -3.91   -29.22   ← 只有这一条坏
其余 5 条乐器轨      <0.006      <0.2%    正常      正常
```

听感为何是「噪音」：99.71% 能量在 DC，去掉后只剩 -29.22dBFS；残余 ZCR 0.4154（白噪量级，音乐 <0.1）、
4–16kHz 占 34.2% 而元音共振峰带只有 4.2% → **完全没有声带/共振峰结构**。
真机复现：同样参数重跑 vocals extract，DC 仍为 +0.6325（99.69%），而 guitar 臂同条件只有 0.0047 → 稳定行为，非偶发。

### 根因链
1. `buildSynthPayload()` 无论用户要不人声，都写死 `lyrics:'[Instrumental]'`（DiT 的**无人声条件**）+ `vocal_language:'unknown'`。
2. 用户 caption 明确写了 "emotional powerful male Japanese rock vocals with layered chorus harmonies" → **条件自相矛盾**。
3. 于是成品本身不含人声，再对它 extract `vocals` → 模型无内容可分离，吐出一片 DC 偏置噪声。
4. 质量档 `/lm` 也一样：把 `[Instrumental]` 喂给 LM，LM 只能按「纯音乐」补全。

### 修复
- 新增 `instrumental` 三元语义（**只有显式 false 才=要人声**，默认保持旧行为逐字节不变），
  从工具 schema → `AudioPlan` → 任务参数 → `buildSynthPayload` 全链路打通。
  要人声时发 `lyrics:''`（引擎语义：**由 LM 生成歌词**）。
- `resolveVocalLanguage()`：显式 `vocalLanguage` > 无人声→`unknown` > caption 日语线索→`ja` > 其他→`en`。
- 质量档同步：`buildQualityLmRequest` 带人声意图；并新增 `applyVocalIntentToQualityRequest`，
  防止 LM 回显 `[Instrumental]` 把意图洗掉。
- **人声护栏**：`resolveStemArmDecision()` 检测「从纯乐器源抽人声」→ 跳过该臂并给出可执行中文提示，
  其余 6 臂照常执行；**绝不静默产出噪声轨**。
- vocals arm 的 caption 从乐器模板改为 a cappella 干声清唱模板。
- **DC 安全网**：`stripDcOffsetFromWav16()` 纯函数，仅当 |均值|>0.05 时逐通道去均值（健康音频按**同一引用**返回，
  位精确不变）。已用用户真实坏文件验证：DC +0.63669 → +0.000012，头/长/格式不变。
  **注**：这只是安全网不是修复——去 DC 后 ZCR 仍 0.336，仍是嘶声，真修复是上面 A+B。

### 修复后真机验证（240s / XL / 质量模式 / 要人声，走修复后的产品函数）
```
/lm 收到 bpm=165 keyscale=A minor timesignature=4 vocal_language=ja lyrics=''
/lm 返回 bpm=165 key=A minor ts=4 lang=ja
         lyrics='[Intro]\nKami ga naki\n\n[Guitar Riff Intro]\n\n[Verse 1]\nYoru no…'  ← 真实日语歌词
对成品做 vocals extract：
  指标                  修复前      修复后
  DC 偏置              +0.6367    0.00203
  DC 能量占比           99.71%      0.01%
  RMS dBFS              -3.91     -15.54
  去DC后 RMS          -29.22     -15.55
  ZCR(去DC)            0.4154     0.1163
  300-1200Hz 共振峰       4.2%     23.78%      ← 人声结构回来了
```
**共振峰带能量提升 5.7 倍、DC 噪声消失** —— 这是「有人声」的客观证据。是否好听需用户试听。

## 2. 缺陷 ②：分轨叠加削顶 + 糊

### 诊断
按工程实际音量叠加 6 条分轨 vs 原曲：

```
sum(stems)  RMS   -3.62dBFS  peak 3.149     ← 严重爆表
整曲        RMS  -17.49dBFS  peak 0.800
电平差      +13.87 dB      削顶采样占比 11.21%
样本相关    +0.296        （真分离应 ≈1.0）
残差能量    相对原曲 +13.51 dB
频段：mid 分轨 15.3% / 原曲 29.4%（缺 14.1pp）
      himid 分轨 14.7% / 原曲 31.2%（缺 16.6pp）
```

**关键发现**：7 个输出文件峰值**逐位相同**（0.99997），而 RMS 从 -13.7 到 -20.7 分散 →
引擎对每个文件**独立做峰值归一化**，分轨之间的相对电平**不携带任何音乐信息**，所以「统一 0.8 推子」必然错。

### 修复（增益分级）
- `placeAudioClip()` 新增可选 `volume`（默认 0.8 保持旧行为）。
- 新增纯函数 `stemPlacementVolume({stemPeak, stemCount, songPeak})`：
  `budget = min(0.9, songPeak)`，`g = min(budget/n, 0.9/stemPeak)`，夹取 [0.02, 1.0]。
  因为 `|Σgᵢxᵢ| ≤ Σgᵢ·peakᵢ`，该式**与相位/相关性无关，永不削顶**。
- 我最初给的两条公式（0.25 下限、等功率 `songRms-10log10(n)`）经实测**都会失败**
  （后者实测峰值 2.372、比原曲响 +18.45dB，因为分轨是**正相干**的，高于 √Σ 模型 +3.58dB，两两相关最高 +0.43）。
  已丢弃，采用上面这条有数学保证的构造。

### 修复后实测
```
                      RMS dBFS            peak          vs 整曲(推子后)
6 stems(含人声)     -3.62 → -19.19    3.149 → 0.525      +13.87 → -1.70 dB
5 条乐器分轨        -8.02 → -22.00    2.578 → 0.515       +9.48 → -4.51 dB
3 条(gtr/bass/drums)          -22.73                    0.535   -5.24 dB
削顶采样占比        11.21% → 0.00%     全部 63 个子集峰值 ≤0.672
```
**分轨现在落在整曲电平的下方 1.7–5.2 dB（随分轨条数变化，公式把固定预算按条数均分），且永不削顶。**

### 诚实的引擎限制（必须让用户知道）
增益分级**只解决了削顶与爆表，没有解决「糊」**。实测：
- 单条分轨在 500–2000Hz 的能量只有原曲同频段的 **0.04–0.55 倍**，该频段与原曲相关性仅 **+0.006…+0.088**
- 增益是线性的，**无法改变频段占比**（修复前后频段完全相同，已实测）
- 分轨之间还两两相关（keys×strings 在 1–6kHz 达 +0.43）→ 它们是**共享低频床的独立重合成近似物，不是原曲的分解**

结论：**`extract` 在这个引擎上无法产出能加回原曲的分轨。** 已在代码注释与 UI 文案中如实写明，
并明确警告「不要再调增益以为修好了糊 —— 要么改 extract，要么换真正的分离模型」。

已加入用户可见的诚实文案（`SongWorkflow.tsx:257` 常驻面板 + 两处 toast）：
「分轨是分别重合成的，不是原曲的严格分解，叠加不会与原曲完全对齐」。

## 3. 缺陷 ③：「一点都不像质量模式」

### 诊断（引擎日志 + 真机 A/B）
质量档把 bpm/keyscale 交给 LM 自由推断（旧注释称「塞给 LM 会导致编曲更暗」）。实测该前提**已不成立**：

| `/lm` 输入 | LM 返回 |
|---|---|
| 仅 caption+duration（旧实现） | bpm=**176**, ts=**6**, lang=**ar** |
| 同上另一次 | bpm=**167**, ts=4, lang=**es** |
| 加上 bpm/keyscale/ts/lang | bpm=**165**, A minor, 4, **ja** |

**LM 的元数据选择是随机的**（83/167/176、拍号 6、语言 ar/es），不是「风格取舍」。
工程网格依赖 bpm，这直接导致成品与 DAW 对不上。

「更暗」假设：4B 模型上**无法复现**（同 seed 对比 centroid −38Hz / −1.1%，低频 −3.2pp，反而略亮）→ 选择正确性优先。

### audio_codes 是否把速度烘进去了？（决定修法）
实测：同一串 codes 在 bpm 83 vs 165 下渲染，**577,463/5,793,463 字节不同** → bpm 仍起作用，但影响弱且靠后；
83-BPM 的节奏性格在重新标记为 165 后依然存活（score 比 1.63）。
架构佐证：`conditioning_target.py:77-86` 把解码后的 codes 作为 **`target_latents`** 喂给 DiT —— **节奏由 LM 写**。
**结论：仅在 `/synth` 事后改 bpm 不足以修复，必须从源头不让 LM 选。** 这正是已实现的方案；
`/synth` 的覆盖仅作第二道保险。

### 修复
- 新增 `withAuthoritativeMetadata()`（纯函数、加法式，未重写 `buildQualityLmRequest`）：
  质量档把工程 bpm/keyscale/timesignature/vocal_language 钉进 `/lm` 与 `/synth`，LM 不得改写。
- `vocalLanguage` 全链路透传（工具 schema → plan → params）。
- 新增 `QUALITY_PEAK_CLIP = 1`：实测 `peak_clip` 是**峰值软限幅强度**（同 codes/seed 只改该值）：
  ```
  peak_clip=100 → 6.70% 帧>0.95（明显削顶）
  peak_clip=10  → 3.09%   （引擎默认，用户遇到的 1.3%）
  peak_clip=1   → 0.52%   ← 采用（RMS 仅降 0.3dB，动态范围不变 20.0dB）
  peak_clip=0   → 0.00%   （= 关闭）
  ```

### 修复后真机验证（240s / XL-sft / 50 步 / 质量模式）
```
/lm  : bpm=165  A minor  ts=4  lang=ja  + 真实日语歌词
/synth: bpm=165  keyscale=A minor  peak_clip=1  steps=50
成品 : 239.2s（=240s）  RMS -15.55dBFS  crest 15.5dB
       0.1s 帧 >0.95 占比 0.33%（修复前 1.3%）
       频段 low 6.8 / lowmid 14.8 / mid 22.2 / himid 33.7 / high 22.4
       人声共振峰带 19.75%
```

### 诚实的质量天花板
实测对比（同 codes/seed，30s）：
```
                      rms     crest   centroid   <120Hz   近静音
快速 turbo 8步/shift3  -14.8   14.8dB   3705Hz     9.5%     3.3%
质量 xl-sft 50步       -16.0   16.0dB   3087Hz     7.3%     0.5%
xl-sft 8步(对照)       -17.0   17.0dB   3252Hz     5.5%     0.3%
```
- 质量模式**确实更好**：crest +1.2dB、低频糊 -2.2pp、**近静音少 6.6 倍**（最可感知的收益）。
- 但 **XL 模型贡献大于 50 步**：xl-sft 8 步已达 0.3% 静音、17.0dB crest，50 步只多 +1.0dB crest 却慢 5.3 倍（585s vs 111s）。
  **50 步对 XL 很可能是错配，建议后续单独调（不在本轮范围）。**
- 残留上限：**单次 240s text2music、无结构条件**（无段落/小节控制、无参考音频、无 repaint）。
  240s 已远超模型稳定范围，编排走向仍会偏通用。
  **诚实的承诺只能是：「速度/调性正确、不再贴顶、空洞更少」，不能承诺「录音室级」。**

## 5. 未验证 / 需用户确认

1. **主观听感未经人耳确认** —— 本环境无法播放音频。所有结论均为客观测量。
   「人声是否好听/咬字是否正确」「分轨是否还糊」必须由用户实际试听。
2. **历史工程不会被自动修复**：`p_7atqcqig` 里那条坏的人声 stem 与旧的 0.8 增益分轨仍留在工程文件里。
   **需要重新生成一次**才能拿到修复后的产物。
3. **未覆盖的分轨入口**：`SongWorkflow.tsx` / `StemGenerateDialog.tsx` 不传 `sourceInstrumental`，
   人声护栏对它们不生效（保持旧行为，不误伤）。如需覆盖需补传来源事实。
4. **等响匹配未实现**：峰值预算不是等响匹配（后者在「频段失真」指标上 57.1pp → 47.2pp 更好），
   但需要额外解码 6×44MB WAV，已记录为后续项。
5. **分轨自身质量的上限未变**：`extract` 无法产出可加回原曲的分轨，这是引擎能力限制，
   本轮只修了「叠加削顶」与「如实告知」，没有也不可能修好「分离度」。
6. **50 步对 XL 可能过采样**，建议后续单独调（未做）。
