# 分轨做不到，是否意味着「局部迭代修改」也做不到？

> 2026-11-13 · 结论：**不是。这是两件不同的事，机制完全不同。**
> `extract`（分轨）走 diffusion 重合成 → 做不到真分离；
> `repaint`（局部重绘）走**掩码 + 源潜变量上下文** → **是真·局部编辑，实测区域外逐样本保留**。
> 复现：`.verify-audio/repaint_probe.py`、`repaint_diag.py`

---

## 一、为什么两者不是一回事

代码里它们共享 `DIRECT_CONDITIONING_TASKS`（`inference.py:36-38`），但**条件方式完全不同**：

| | `extract`（分轨） | `repaint`（局部重绘） |
|---|---|---|
| 条件方式 | 整段源音频当 context + 文本指令 | **二值掩码**：区域内置 1（生成），区域外置 0（保留原潜变量） |
| 输出目标 | 一整条"该乐器"的新音频 | **同一段音频**，只在掩码区替换 |
| 需要分离能力 | **是**（必须有分离网络） | **否**（只要能在掩码区延续上下文） |
| 区域外是否保留 | 无此概念 | **是，逐样本保留** |

分轨失败的原因是「没有分离网络，只能凭提示重合成」。
局部编辑**不需要分离**——它只需要"在指定时间区间里，用前后文约束重新生成那一段"，这是 diffusion inpainting 的经典能力。

## 二、实测：repaint 是真局部编辑

用用户真实的 240s 质量模式成品，重绘 **60–75s** 区间，把描述换成完全不同的风格（爵士三重奏）。

```
=== 区域 60-75s 改成爵士三重奏
  源 240.00s  输出 240.00s  时长差 +0.000s        ← 时长严格保持
  区域外（225.0s） 相关 +1.0000   RMS 差 -0.00 dB   ← 未改动部分原样保留
  区域内（ 15.0s） 相关 +0.1058   RMS 差 +0.06 dB   ← 真的被改写了
```

逐样本（int16 单位）核对：

```
区域外 逐样本最大差 1（=1 个量化单位）  完全相同 82.85%
区域内 逐样本最大差 47047            完全相同 0.00%
```

**区域外最大偏差只有 1 个 int16 量化台阶**（即浮点转 int16 的舍入），82.85% 的样本逐字节相同。
这条判据说明它是**真正的局部编辑**，不是整段重生成。

再测「只改歌词」（caption 保持日式摇滚，lyrics 换成新写的日文段落）：

```
区域外 相关 +1.0000   区域内 相关 +0.0878
区域外 max差 1        区域内 max差 49975
```

同样只有区域被改动。

| 你的诉求 | 能否做到 | 用什么 | 实测/说明 |
|---|---|---|---|

| **3. 局部某个范围歌词** | ✅ **能** | `repaint` + 新 `lyrics` | 已验证：同上，区域外严格保留 |
| **4. 局部某个范围的编曲** | ✅ **能** | `repaint` + 新 `caption` | 已验证：换成爵士三重奏生效 |
| **5. 添加某些乐器** | ⚠️ **能"加"，但是整曲级** | `lego` + `track` | `lego` 是"按上下文生成一条新乐器轨"，它能叠加出乐器，但**无法指定"只在 30–60s 加"**；且它是重合成，不是从原曲里长出来的 |
| **1. 修改部分乐器轨道** | ❌ **不能** | — | 这**依赖分轨**：必须先分离出某条乐器，才能只改它。既然 `extract` 做不到真分离，"只改贝斯不改鼓"就不可能 |

### 结论一句话
- **跟"时间范围"有关的局部编辑（2/3/4）→ 可行，且已验证是真局部**
- **跟"乐器分离"有关的局部编辑（1）→ 不可行**，因为它的前提就是分轨
- **加乐器（5）→ 能加但只能整曲叠加**，不是"在某个区间加"

## 四、发现一个真实产品 bug（顺手查出来）

`scripts/companion.mjs:1047` `buildRepaintRequest()` **没有发 `task_type: 'repaint'`**：

```js
export function buildRepaintRequest(params = {}) {
  return {
    caption: params.caption,
    lyrics: '[Instrumental]',
    seed: ...,
    batch_size: 1,
    repainting_start: params.startSec,
    repainting_end: params.endSec,
    inference_steps: 50,
    guidance_scale: 1.0,
    shift: 1.0,
    // ← 没有 task_type，也没有 duration
  }
}
```

后果实测：
- **没有 `task_type`** → 引擎回落 `text2music`，**掩码被完全忽略**，变成整段重新生成
  （实测：区域外相关从 1.0000 掉到 **+0.0076**，频谱偏差 17.09 pp，且任何时移都找不到匹配）
- **没有 `duration`** → 240s 的源只渲染出 **30s**（实测输出 30.00s，时长差 -210s）

这和之前 `{lego: arm}` 是**同一类 bug**：请求体字段与引擎 schema 不一致。
产品里的"重绘"功能目前**实际上是坏的**（用户点重绘 = 整首歌被重新生成一遍，还可能被截成 30s）。

修复很小（两行：补 `task_type:'repaint'` + 透传 `duration`），但**本轮我没有改代码**，
先等你确认方向——因为一旦修好，用户就会开始用局部编辑，而"改乐器"（诉求 1）仍然做不到，
需要在 UI 上说清楚边界。

## 五、建议的产品形态

修好 `repaint` 后，可以诚实提供：

1. **局部重绘**（改旋律/歌词/编曲）—— 真能力，已有代码路径，修 2 行即可用
2. **加乐器**（`lego`）—— 真能力，但定位为"整曲叠加一条新乐器"，不能说"在某区间加"
3. **改某个乐器**（诉求 1）—— **不能**。要做得先引入 Demucs 之类的真分离模型
   （见 `STEM_SEPARATION_FEASIBILITY.md`）
4. **整曲重生成**（`cover`）—— 保结构换编制，真能力

如果用户既要"改某个乐器"又要"局部"，那**必须**先上真分离模型：
分离 → 改单轨 → 再混回去。这条链路的每一步都是成熟技术，只是需要新模型。
