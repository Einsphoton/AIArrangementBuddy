# 三线融合路线：语料 × 检索 × 模型

> 目标：让本项目的 AI 编曲在 **日摇 / 英伦摇滚 / 美式 Hardcore / JRPG 配乐** 四类风格上，
> 从「和弦对但难听」提升到「像人写的原创」。
>
> 三条线不是三个项目，而是同一个系统的三层。本文说明它们各自负责什么、怎么并行、在哪汇合。
> 相关：`docs/MIDI_CORPUS_STYLE_LEARNING.md`（可行性与边界）、`scripts/corpus/`（语料管线）、`scripts/crawl/`（采集）。

---

## 0. 一句话结论

**质量不由「最大模型」决定，而由「判别层」决定。**

语料层决定「见过什么」，检索层决定「用得上什么」，模型层决定「能生成什么」，
而最终听众听到的那个版本，是从 N 个候选里**挑**出来的——挑的能力（判别器）比生的能力（生成器）更容易做好，也更能立刻提升听感。

---

## 1. 系统分层与依赖

```
┌─ ① 语料层 ──────────────────────────────────────────────────┐
│  GigaMIDI（申请中）· MetaMIDI/Lakh · VGMusic 爬虫            │
│  · 你自己的 Guitar Pro（convert-gp.mjs → MIDI）              │
│  · 已有收藏                                                   │
└───────────────────────┬──────────────────────────────────────┘
                        │  normalization + quality gate
┌─ ② 画像层（已实现）─────────────────────────────────────────┐
│  scripts/corpus → 风格画像 JSON（分位数 / 分布 / 功能进行）   │
└───────────────────────┬──────────────────────────────────────┘
                        │
┌─ ③ 检索层（RAG，P2）────────────────────────────────────────┐
│  片段库（4/8 小节）· 索引 · search_reference 工具             │
│  + 风格 Skill（markdown 工作流，注进系统提示）                │
└───────────────────────┬──────────────────────────────────────┘
                        │ 意图 JSON（不含音符）+ few-shot 参考
┌─ ④ 规划层（现有 LLM Agent）─────────────────────────────────┐
│  曲式 / 和弦进行 / 配器 / 动机计划 / 每段织体选择             │
└───────────────────────┬──────────────────────────────────────┘
                        │
┌─ ⑤ 实现层（packages/core 生成器）───────────────────────────┐
│  按 profile 采样参数 + 乐理约束，把意图渲染成音符             │
└───────────────────────┬──────────────────────────────────────┘
                        │ 4~8 个候选
┌─ ⑥ 判别层（P1.5）───────────────────────────────────────────┐
│  styleScore（硬伤 + 风格贴合）→ 重排 → top-1                  │
└───────────────────────┬──────────────────────────────────────┘
                        │
        ┌───────────────┴───────────────┐
        │ ⑦ 模型层（可选，补充候选源）   │  MIDI-GPT / AMT
        │  不参与主路径，只贡献候选      │
        └───────────────────────────────┘
```

**关键约束**：④ 的输出里**不能有音符**。模型只做「选和弦、定结构、挑织体、编动机」，音符由 ⑤ 落地。
现在 `apps/server/src/tools/` 的 `write_notes` 让模型直接写音符，是当前质量天花板的主要来源。

## 2. 模型层的真实定位（先纠正预期）

| 模型 | 训练数据 | 输出形态 | 对四类风格的适配度 | 建议 |
| --- | --- | --- | --- | --- |
| **MIDI-GPT** | GigaMIDI（210 万，多轨 MIDI） | **多轨 MIDI**，属性可控（风格/乐器/密度） | ⭐⭐⭐⭐ 最对口。GigaMIDI 仓库自带 `MIDI-GPT-Loop` 代码 | **首选**：先做推理当候选源，之后再谈微调 |
| **Anticipatory Music Transformer** | Lakh MIDI，≤1.28 亿参数 | MIDI，强项是 **accompaniment / infilling**（给旋律配伴奏、填空） | ⭐⭐⭐ 能力对口「给旋律配编曲」；但只在 20 秒片段上有人评 | **次选**：需要 GPU 推理 |
| **NotaGen** | 160 万份 ABC + 9K 古典微调 + DPO | **ABC 记谱文本**，古典钢琴 | ⭐ 输出形态不匹配（不是多轨 MIDI），且只覆盖古典 | **不推荐**做一期 |
| Music Transformer / 其它钢琴模型 | MAESTRO 等 | 单轨钢琴 | ⭐ | 只用于演奏层参考 |

**结论：模型是「第七层」，不是主路径。** 主路径永远是 ②→③→④→⑤→⑥。
把模型当主路径，会重演「训练三个月、产出还不如规则生成器」的经典失败。

## 3. 并行排期（按周）

三条线可以同时推进，汇合点在 P2（检索层）。**互不阻塞**，这才是"并行融合"的正确含义。

| 周 | 线 A：语料 | 线 B：检索 / 生成 | 线 C：模型 | 交付物 |
| --- | --- | --- | --- | --- |
| **W1** | GigaMIDI 提交访问申请；`pnpm crawl:run` 抓 VGMusic；整理已有收藏 | 读 `generators/index.ts`，列出待参数化的常量清单 | 环境探查：本地有没有 GPU / 显存多大 | 首批 500~2000 个 MIDI + 常量清单 |
| **W2** | 各站适配器（freemidi / kunstderfuge）；GP 批量转换 | 新增 `packages/core/src/style/profile.ts`（类型 + 采样 + fallback） | 若 GigaMIDI 已批：先只下元数据 | 2 个风格 profile + profile 类型 |
| **W3** | 质量闸门调参；人工听检 100 首建金标 | 生成器参数化接入 profile（保留旧常量 fallback） | MIDI-GPT 推理跑通（若 GPU 可用） | 盲测 A/B 第一版 |
| **W4** | 四类风格 profile 齐（jrpg / j-rock / britpop / post-hardcore） | 片段库构建（4/8 小节切分 + 特征索引） | AMT 推理跑通 | 检索层初版 |
| **W5** | 金标扩展到 300 首 | `search_reference` Agent 工具 + 意图 JSON schema | 模型候选接入管线（只做候选源） | 端到端：检索→规划→实现 |
| **W6** | 偏好数据开始积累（界面 A/B 按钮） | `styleScore` 判别器 + 多候选重排 | — | 盲测偏好率目标 ≥60% |
| **W7+** | GigaMIDI 分片下载（若批准） | 段落/动机结构（第二优先级） | 重排器训练 / LoRA 评估 | 稳定迭代 |

**并行原则**：线 A 慢但可预期（下载/申请/清洗），线 B 是主线（每周都有可听结果），线 C 是期权（有 GPU 就做，没有不阻塞）。

## 4. 每层的验收标准（必须可量化）

| 层 | 验收标准 | 测量方式 |
| --- | --- | --- |
| ① 语料 | 每风格 ≥500 首通过质量闸门；`noDrums` 占比 <40% | `ledger.jsonl` 统计 |
| ② 画像 | 画像字段可回指音乐概念；同一批语料两次构建结果一致 | `pnpm corpus:selftest` + 人工看 3 个字段 |
| ③ 检索 | 给定和弦进行，top-3 参考片段人工判定「风格对」的比例 ≥70% | 抽 30 个查询人工打分 |
| ④ 规划 | 输出 JSON 可被 ⑤ 无损渲染（无字段缺失/非法） | schema 校验 + 单测 |
| ⑤ 实现 | 生成结果与画像的分布距离（音级/节奏 n-gram/密度）< 基线 | `styleScore` 客观指标 |
| ⑥ 判别 | 多候选重排后，盲测偏好率 ≥60%（vs 单候选） | A/B 盲测 20 组 |
| ⑦ 模型 | 作为额外候选时，能进入 top-1 的比例 ≥15% | 离线统计 |

**任何一层没达标，就不要进入下一层。** 这是防止「同时开五个坑、哪个都不深」的唯一办法。

## 5. 风险与对策

| 风险 | 触发概率 | 对策 |
| --- | --- | --- |
| GigaMIDI 申请被拒 / 拖很久 | 中 | 线 A 先用 VGMusic + 已有收藏 + GP 转换跑起来，不等它 |
| 四类风格的真实可用语料远少于预期 | 高 | 金标优先（300 首精修 > 3 万首垃圾）；JRPG 走「动机 + 和声」单点突破 |
| 生成器参数化后回归现有风格 | 中 | profile 全部 fallback 到旧常量；A/B 开关；每次改动跑 `pnpm test` |
| 判别器过拟合到少数金标 | 中 | 强制分风格、分来源留出验证集 |
| 模型推理太慢/显存不够 | 中 | 只用它做离线候选池（batch），不进实时循环 |
| 一直不收敛 | 中 | 每两周做一次盲测；连续两次 <55% 就回退该层 |

`rock → j-rock / post-hardcore / britpop`、`cinematic → jrpg`、`pop → britpop`，可按需调整。

## 附：为什么不是「先训模型再说」

| 做法 | 首次可听结果 | 达到「像」的概率 | 沉没成本 |
| --- | --- | --- | --- |
| 先训模型 | 1~3 月 | 低（缺百万级语料） | 高 |
| 先做语料 + 检索 + 重排 | **1~2 周** | **高** | 低（每步可回滚） |

在拿到百万级语料和 GPU 之前，「训模型」是一条没有反馈的长隧道；
而检索 + 重排是每周都能听见进步的短循环。**先走短循环。**
